# Test Writing

自動テストを書くための手順です。Google Testing Blog と『Software Engineering at Google』（テストのサイズ、振る舞いのテスト、テストダブルの使い方、不安定なテスト）、Gerard Meszaros の『xUnit Test Patterns』（テストダブルの分類）、ISTQB Foundation Level シラバス v4.0（テスト設計技法）、Testing Library の指針、StrykerJS（ミューテーションテスト）をもとにしています。

この文書では、テストで確かめる対象のコード（関数・クラス・コンポーネント・API など）を「テスト対象」と呼びます。

## 基本ルール

1. **期待値は仕様から決める。** テスト対象の実装を読んで、現在の出力をそのまま期待値に写しません。実装を写したテストは、実装が間違っていても通ります。例外は特性テストだけです（手順 2 を参照）。
2. **実装ではなく振る舞いをテストする。** テスト対象の利用者が使う入口（公開されたメソッド、画面の操作、HTTP の要求、コマンドの引数）から呼び、利用者に見える結果（戻り値、画面の表示、応答、保存されたデータ）を確かめます。private なメソッドを直接呼んだり、内部のメソッドの呼び出し順を確かめたりしません。
3. **書いたテストが、コードを壊したときに落ちることを確かめる。** 落ちないテストは、通っていても何も確かめていません。
4. **テストが落ちたら、テスト側を書き換えて通さない。** 落ちた理由がテスト対象の不具合なら、そのまま利用者に報告します。テストの書き間違いなら直しますが、期待値を変える場合は根拠を書きます。
5. **本番のコードの振る舞いを変えない。** テストを書くために本番のコードの変更（依存を外から渡せるようにする、など）が必要な場合は、変更の内容を示して利用者の了承を得ます。構造の変更は safe-refactoring の手順で行います。
6. **プロジェクトの既存のテストに合わせる。** フレームワーク、ファイルの置き場所、命名、ヘルパー、テスト用のデータの作り方は、既存のテストに従います。規則が無い場合だけ、この文書の書き方を使います。

## 手順

### 1. プロジェクトの形を確かめる

テストの書き方は、ソフトウェアの種類と、外部とのつながり方によって変わります。書き始める前に次を確かめます。

- **テストの実行方法:** `package.json` の `scripts`、`angular.json` の `test` の設定、`vitest.config.*`・`jest.config.*`・`karma.conf.*`、`pytest.ini`、`*.csproj` などから、テストのフレームワークと実行コマンドを特定します。見つからなければ利用者に尋ねます。
- **既存のテスト:** テストファイルの置き場所と命名、共通のヘルパー、テスト用のデータ（フィクスチャ）、既存のテストダブルを確認します。同じ種類のテスト対象をテストしている既存のファイルを 1〜2 件読み、書き方を合わせます。
- **ソフトウェアの種類:** ライブラリ・CLI・Web API・画面（SPA など）・MCP サーバー・バッチ処理のどれか。種類ごとの入口は「ソフトウェアの種類ごとのテストの入口」を見ます。
- **外部とのつながり:** テスト対象が使う外部のもの（DB、HTTP 通信、ファイル、現在時刻、乱数、環境変数、タイムゾーン、ロケール、メッセージキュー）を挙げます。手順 5 でテストダブルを選ぶときと、手順 7 で結果を安定させるときに使います。
- **取り決め:** `CLAUDE.md`・`AGENTS.md`・`CONTRIBUTING.md` があれば読みます。

### 2. 依頼の種類を見分ける

依頼の種類によって、期待値の決め方と手順の順序が変わります。

| 依頼の種類 | 期待値の決め方 | 手順の違い |
|---|---|---|
| 新しい機能のテスト | 仕様・issue・利用者の説明から決める | 利用者が求めた場合は、テストを先に書き、落ちることを確かめてから実装する（テスト駆動開発） |
| バグ修正の再現テスト | 正しい振る舞いを期待値にする | 修正の前にテストを書き、落ちることを確かめる。修正後に通ることを確かめる。周辺の既存のテストもすべて実行する |
| 既存のコードへの後付け | 仕様・ドキュメント・型・呼び出し元から決める | 仕様が見つからない期待値は、根拠を利用者に確かめる。確かめられない場合は「現在の挙動を記録したもの」とテスト名かコメントに明記する |
| リファクタリング前の特性テスト | テスト対象の現在の出力を期待値にする | 現在の挙動がバグに見えても、そのまま記録し、報告で指摘する。出力が大きい場合は、入力の集合を用意して出力をファイルに保存し、変更後に比べる（ゴールデンマスター） |

### 3. テストのサイズと入口を選ぶ

テストの種類は、確かめる範囲（スコープ）と、テストが使う資源（サイズ）の 2 つで決まります。

| サイズ | 使ってよい資源 | 主な用途 |
|---|---|---|
| Small | 1 つのプロセスの中だけ。ネットワーク、ファイル、スリープを使わない | 計算・分岐・データ変換・状態の変化 |
| Medium | 1 台のマシンの中。localhost への通信、ローカルの DB やファイルを使ってよい | 自分のコードと DB・HTTP サーバー・ファイルとの組み合わせ |
| Large | 制限なし。複数のマシン、外部のサービス | 利用者の操作を最初から最後まで通す |

- **確かめたい振る舞いを確かめられる、最も小さいサイズを選びます。** サイズが大きいほど、実行が遅く、結果が不安定になりやすく、落ちたときに原因の場所を特定しにくくなります。
- **ただし、小さくするためにテストダブルを増やしすぎないようにします。** 自分たちのコード同士をすべてテストダブルに置き換えた Small のテストは、組み合わせたときの不具合を見逃します。画面のコンポーネントや Web API では、DB や HTTP 通信だけを置き換えて、自分たちのコードは本物のまま組み合わせるテストが、最も効果が高いことが多くあります。
- テストの入口は、テスト対象が実際に使われる方法に近づけます。Testing Library の指針は「テストがソフトウェアの使われ方に近いほど、テストから得られる確信は大きくなる」としています。

### 4. テストケースを設計する

テストを書く前に、テストケースを表にします。依頼が「テストを書いて」だけでも、この表を先に作ります。

1. テスト対象の振る舞いを、公開された入口の単位で挙げます。1 つのメソッドに複数の振る舞いがあれば、分けて挙げます。
2. 振る舞いごとに、下の設計技法を当てはめてテストケースを導きます。
3. 各テストケースに、入力・期待値・導いた技法・期待値の根拠を書きます。

| ID | 振る舞い | 入力・前提 | 期待値 | 技法 | 期待値の根拠 |
|---|---|---|---|---|---|
| T1 | 年齢から料金区分を返す | 年齢 12 | 子ども料金 | 境界値 | 仕様書 3.2「12 歳以下は子ども料金」 |

テストケースが 20 件を超える場合や、期待値の根拠が見つからないテストケースがある場合は、書く前に表を利用者に示して確かめます。

#### 設計技法

| 技法 | 使う場面 | テストケースの導き方 |
|---|---|---|
| 同値分割 | 入力の値の範囲や種類によって結果が変わる | 同じ結果になる入力のまとまり（有効なものと無効なもの）を作り、各まとまりから代表の値を 1 つずつ選ぶ |
| 境界値分析 | 範囲に順序のある入力（数値、文字数、日付、件数） | 各境界について、境界の値とその両隣の 3 つの値を選ぶ（3 値境界値分析）。`<` と `<=` の取り違えを見つけられる |
| デシジョンテーブル | 複数の条件の組み合わせで結果が変わる | 条件の組み合わせと結果を表にし、組み合わせ（ルール）ごとに 1 つのテストケースを作る。表を作る過程で、仕様に書かれていない組み合わせも見つかる |
| 状態遷移テスト | 状態を持ち、操作によって状態が変わる（注文の状態、画面のモード、接続の状態） | 状態と遷移を図にし、すべての正しい遷移を 1 回ずつ通す。加えて、許されない操作（発送済みの注文の取り消しなど）が拒否されることを確かめる |
| ペアワイズ法 | 設定やオプションの組み合わせが多すぎて、すべては試せない | すべての 2 つの因子の値の組み合わせが、どこかのテストケースに 1 回以上現れるように選ぶ |
| ループの回数 | 繰り返しを含む処理 | 0 回・1 回・2 回・上限の回数・上限を超える回数で試す |
| エラー推測 | すべての振る舞いに追加で当てはめる | 下のチェックリストから、テスト対象に当てはまるものを選ぶ |

#### エラー推測のチェックリスト

- `null`・`undefined`・空文字列・空白だけの文字列・空配列・空オブジェクト
- `0`・負の数・小数・非常に大きな数・`NaN`
- 絵文字・結合文字・全角と半角・改行を含む文字列、非常に長い文字列
- 重複したデータ、同じ要求の 2 回目
- 月末・うるう年・タイムゾーンの違い・日付をまたぐ時刻
- HTTP の失敗（4xx・5xx）・タイムアウト・応答の形が想定と違う場合
- 権限が無い・ログインしていない状態
- 同じデータを 2 つの処理が同時に更新する場合、応答の到着順が入れ替わる場合

### 5. テストを書く

#### テストの形

- **1 つのテストでは 1 つの振る舞いを確かめます。** テスト名には、条件と期待する結果を書きます（例: `12 歳以下なら子ども料金を返す`）。テスト対象のメソッド名だけをテスト名にしません。
- **準備・実行・確認の 3 つに分けて書きます（Arrange-Act-Assert）。** プロジェクトが Given-When-Then の形を使っていれば、それに合わせます。
- **入力だけが違う同じ振る舞いは、パラメータ化します**（`it.each`、`test.each`、`[TestCase]`、`@pytest.mark.parametrize` など）。入力と期待値を表の形で並べます。
- **テストの中に `if` やループを書きません。** 期待値を計算する処理をテストに書くと、テスト対象と同じ間違いをテストもすることがあります。期待値は具体的な値で書きます。
- **確認は、利用者に見える結果に対して行います。** 戻り値、画面の表示、HTTP の応答、保存されたデータを確かめます。
- **準備のコードが長くなる場合は、テスト用のデータを作る関数（ビルダー）やフィクスチャに分けます。** ただし、そのテストの結果に関わる値は、テストの中に書いて見えるようにします。
- **作ったものは片付けます。** 一時ファイル、起動したサーバー、DB に入れたデータ、変更した環境変数やグローバルな状態は、テストの後で元に戻します。

#### テストダブルの選び方

テストダブルは、テストのために本物の依存の代わりに使うものの総称です。『xUnit Test Patterns』では次の 5 つに分けています。

| 種類 | 役割 | 使う場面 |
|---|---|---|
| ダミー | 引数を埋めるだけで、使われない | テスト対象が必要とするが、この振る舞いには関係ない引数 |
| スタブ | 決まった値を返す | テスト対象への入力を制御したいとき（API が空の一覧を返す場合、など） |
| スパイ | 呼ばれ方を記録し、テストの後で確かめられるようにする | 呼ばれたこと自体が振る舞いであるとき |
| モック | 期待する呼ばれ方をあらかじめ設定し、違えば失敗する | 呼ばれ方自体が振る舞いで、設定と確認を 1 つにまとめたいとき |
| フェイク | 本番には使えないが、実際に動く簡易な実装 | 本物が遅い・準備が重い依存（メモリ上の DB、メモリ上のファイルシステム） |

次の順で選びます。

1. **本物を使えるなら本物を使います。** 速く、毎回同じ結果を返す依存（純粋な関数、値オブジェクト、自分たちのコードのクラス）は置き換えません。
2. **本物が使えない場合は、フェイクを検討します。** プロジェクトにすでにフェイクがあれば、それを使います。
3. **入力を制御したいだけなら、スタブを使います。**
4. **スパイとモックは、呼ばれ方そのものが利用者に見える結果であるときだけ使います。** メールの送信、監査ログの記録、外部への通知などです。内部の補助クラスのメソッドが何回呼ばれたかは確かめません。テストが実装の変更のたびに落ちるようになり、リファクタリングを妨げます。
5. **自分たちが所有していない型（外部ライブラリや外部 API のクライアント）は、直接モックしません。** 自分たちの側に薄いラッパーを作り、ラッパーをテストダブルに置き換えます。外部ライブラリの振る舞いを推測でモックすると、本物と違う動きをするテストダブルができます。

テストダブルが 3 つ以上必要になる場合は、テスト対象の責務が多すぎる可能性があります。報告にそのことを書きます。

#### 結果を毎回同じにする

- 現在時刻・乱数・タイムゾーン・ロケールに依存する処理では、それらをテストから固定します（フェイクタイマー、時刻を外から渡す、乱数の種を固定する）。
- 一定時間待つ `sleep` や `setTimeout` を書きません。条件が満たされるまで待つ仕組み（`waitFor`、`await` で完了を待つ、フェイクタイマーを進める）を使います。
- 他のテストの結果や実行順に依存しないようにします。各テストは、単独で実行しても通るようにします。
- 外部のネットワークに接続しません。

#### 画面のテスト

- 要素は、利用者が見つける方法で探します。ロール・ラベル・表示されているテキストを使い、CSS のクラス名や DOM の構造には依存しません。どうしても探せない場合だけ `data-testid` を使います。
- 操作は、利用者の操作と同じ形で行います（クリック、入力、キー操作）。コンポーネントの内部の状態やメソッドを直接操作しません。
- スナップショットテストは、小さく、変化の少ない出力にだけ使います。大きなスナップショットは差分を誰も読まなくなり、更新のたびにそのまま受け入れられて、何も確かめないテストになります。

### 6. テストが落ちることを確かめる

書いたテストが本当に不具合を見つけられるか、テスト対象を一時的に壊して確かめます。

1. テストを実行し、通ることを確かめます。
2. 新しく書いたテストごとに、そのテストが確かめているはずの箇所を 1 か所だけ壊します。例: 条件を反転する、`<` を `<=` にする、戻り値を固定の値にする、エラー処理の分岐を消す、呼び出しを消す。
3. テストを実行し、落ちることを確かめます。落ちなければ、そのテストは何も確かめていないので、確認の仕方を直します。
4. 壊した箇所を元に戻します。`git diff` で、本番のコードに変更が残っていないことを確かめます。

- バグ修正の再現テストでは、修正前のコードでテストが落ちることが、この確認になります。
- プロジェクトに StrykerJS などのミューテーションテストのツールが設定されている場合は、変更したファイルに絞って実行し、生き残ったミュータント（コードを変えても落ちるテストが無かった箇所）を報告します。設定されていない場合に、利用者の了承なくツールを導入しません。
- カバレッジは、テストが通っていない分岐を見つけるために使います。カバレッジの数値を上げること自体を目的にしません。行を通っていても、結果を確かめていなければ不具合は見つかりません。

### 7. 結果が安定しているか確かめる

- 新しく書いたテストを、単独で 1 回、テスト全体の中で 1 回実行します。
- 新しく書いたテストを 3〜5 回繰り返し実行し、毎回同じ結果になることを確かめます。テストランナーに実行順を無作為にする設定があれば、それも使います（Vitest の `--sequence.shuffle`、Jasmine の `random: true` など）。
- 1 回でも結果が変わったら、手順 5 の「結果を毎回同じにする」に戻って原因を直します。原因が分からない場合は、報告に書きます。

### 8. 報告する

```markdown
## Test Writing Report

- 対象: src/pricing/fare.ts の calculateFare()
- 依頼の種類: 既存のコードへの後付け
- テストのサイズ: Small（外部の依存なし）
- 追加したファイル: src/pricing/fare.spec.ts

### テストケース
| ID | 振る舞い | 入力・前提 | 期待値 | 技法 | 期待値の根拠 |
|---|---|---|---|---|---|

### 確認の結果
- テストの実行: 12 件成功 / 0 件失敗
- 壊して落ちることの確認: 12 件中 12 件が落ちた
- 繰り返し実行: 5 回とも同じ結果
- 本番のコードの変更: なし

### テストしていない範囲
- 外部の料金 API が遅延した場合（Medium のテストが必要）

### 気付いた点
- 年齢が負の数のとき、エラーにならず大人料金を返す。仕様に記載が無いため、現在の挙動のままテストしていない。
```

## ソフトウェアの種類ごとのテストの入口

| 種類 | テストの入口 | 外部の依存の扱い |
|---|---|---|
| ライブラリ | 公開された関数・クラス | 多くは依存なし。入力と出力の関係が常に成り立つ性質（並べ替えても要素数は変わらない、など）があれば、fast-check などのプロパティベーステストで多数の入力を自動生成して確かめる |
| CLI | プロセスを起動し、引数・標準入力を与える | 標準出力・標準エラー出力・終了コードを確かめる。ファイルは一時ディレクトリに作る |
| Web API | HTTP の要求を、プロセス内またはローカルのサーバーに送る | DB はコンテナで動かす本物か、フェイクにする。他のサービスとの間で要求と応答の形を約束している場合は、契約テストで双方の食い違いを確かめる |
| 画面（SPA） | コンポーネントを描画し、利用者と同じ操作をする | HTTP 通信は、テスト用の HTTP の仕組み（Angular の `HttpTestingController`、MSW など）で応答を固定する |
| MCP サーバー | MCP のクライアントからツールを呼ぶ（SDK のメモリ上の通信を使う） | `tools/list` の応答のスキーマ、成功時の結果、失敗時の `isError: true` を確かめる |
| バッチ処理・データ移行 | 入力のデータを用意して処理を実行する | 処理の前後で件数と中身を比べる |

### Angular の場合

- Angular 21 以降の新しいプロジェクトでは Vitest が標準のテストランナーですが、Karma と Jasmine も引き続きサポートされています。どちらを使うかは、プロジェクトの設定に従います。
- 時間の経過に依存する処理は、フェイクタイマー（`fakeAsync` / `tick`、`vi.useFakeTimers()`）で時間を進めます。
- RxJS のストリームで、時間と値の順序が振る舞いである場合は、`TestScheduler` によるマーブルテストを使います。

## このスキルで扱わないこと

次のテストは、自動テストのコードを書く作業とは別の手段が必要です。依頼された場合は、その旨と、使える手段を伝えます。

- 負荷・性能・耐久のテスト（k6、JMeter などの専用のツール）
- 脆弱性診断・ペネトレーションテスト（専用のツールと専門家）
- ユーザビリティテスト・アルファテスト・ベータテスト・受け入れの判断（実際の利用者が必要）
- 実機・複数のブラウザでの確認（BrowserStack などの実機のクラウド、web-compat-mcp でのブラウザ対応状況の確認）

## 行わないこと

- テストを通すために、根拠なく期待値を書き換えること。
- 確認（`expect`・`assert`）の無いテスト、`expect(true).toBe(true)` のように常に通るテスト、例外を `catch` して握りつぶすテストを書くこと。
- カバレッジの数値を上げるためだけに、結果を確かめないテストを書くこと。
- `it.only`・`fdescribe`・`it.skip`・`xit` などをテストに残すこと。
- 本番のコードを、了承なくテストのために変更すること。
