# Safe Refactoring

コードの外部から見える振る舞いを変えずに内部の構造を改善するための手順と、操作のカタログです。Martin Fowler の『リファクタリング』の分類（コードの臭い = 改善が必要なことを示す兆候）に沿っています。

## 基本ルール

すべての操作に次の 5 つを適用します。

1. **振る舞いを変えない。** 戻り値・例外の型と発生条件・副作用（DB 書き込み、ログ、HTTP 応答）・公開 API のシグネチャ・実行順序を「振る舞い」に含めます。
2. **1 回の変更で行う操作は 1 つだけにする。** 「関数の抽出」と「名前の変更」を同時に行いません。
3. **変更の前と後でテストを実行する。** 型チェックと lint も合わせて実行します。
4. **テストが落ちたら、直そうとせずに変更を戻す。** 戻してから原因を調べ、操作をさらに小さく分けてやり直します。
5. **テストが無い箇所は、先に特性テスト（Characterization Test）を書く。** 現在の出力を正解として記録するテストです。現在の挙動がバグに見えても、そのまま記録します。書き方は test-writing の手順に従います。

## 手順

### 1. 前提を確かめる

- テストを実行するコマンドを特定します（`package.json` の `scripts`、`pytest`、`dotnet test` など）。見つからなければ利用者に尋ねます。
- 型チェックのコマンドも特定します（`tsc --noEmit`、`mypy`、`dotnet build`）。
- 変更を戻せる状態か確かめます。git なら `git status` で作業ツリーに未コミットの変更が無いことを確認します。未コミットの変更があれば、先にコミットするか退避するか利用者に尋ねます。

### 2. ベースラインを取る

テストを実行し、すべて通ることを確かめます。落ちているテストがあれば、リファクタリングを始めずに利用者に報告します。落ちている状態からは、変更で何が壊れたか区別できないためです。

### 3. 臭いを特定する

下の「操作カタログ」の「見つけ方」の列を使って、対象コードにある臭いを挙げます。

- 利用者が操作を指定している場合（「この関数を分割して」）は、その操作だけを行います。
- 指定が無い場合（「この辺をきれいにして」）は、見つけた臭いを一覧にし、効果が大きい順に並べて、どれから着手するか利用者に選んでもらいます。

### 4. 操作を 1 つ適用する

- 適用前に、変更するファイルと関数・クラスの名前を宣言します。
- 「振る舞いが変わりうる操作」（後述）に当たる場合は、何が変わるかを説明し、利用者の了承を得てから適用します。
- 名前の変更や移動では、参照しているすべての箇所を検索して一緒に直します。文字列で参照している箇所（テンプレート、設定ファイル、リフレクション、DI の登録）も検索します。

### 5. テストを実行する

- テスト・型チェック・lint を実行します。
- 通った場合: 結果を報告し、コミットの区切りにすることを提案します。
- 落ちた場合: `git restore <ファイル>`（または `git checkout -- <ファイル>`）で戻します。git が無い環境では、手順 4 の前に対象ファイルを複製しておき、その複製で戻します。戻した後、落ちたテスト名とエラー文を添えて報告します。

### 6. 次の操作に進む

手順 3 に戻ります。1 操作ごとに手順 5 を通します。

## 報告の形式

各操作のあとに、次の形式で報告します。

```markdown
## Refactoring Report
- 操作: 関数の抽出（Extract Function）
- 対象: src/order/order.service.ts の calculateTotal()
- 変更前のテスト: 128 件成功 / 0 件失敗
- 変更後のテスト: 128 件成功 / 0 件失敗
- 型チェック: エラーなし
- 振る舞いが変わりうる点: なし
- 次の候補: calculateTotal() 内の条件式の分解
```

## 振る舞いが変わりうる操作

次の操作は、名前の印象に反して振る舞いを変えることがあります。適用前に、該当する点を利用者に説明して了承を得ます。

| 操作 | 変わる点 |
|---|---|
| `a && a.b` を `a?.b` に書き換える | `a` が `0`・`''`・`false` のとき、元は `a` の値を返し、書き換え後は `undefined` を返す |
| `a \|\| b` を `a ?? b` に書き換える | `a` が `0`・`''`・`false` のとき、元は `b` を返し、書き換え後は `a` を返す |
| Promise チェーン・同期関数を async/await にする | 同期的に投げていた例外が Promise の reject になる。呼び出し側の戻り値の型が `Promise` / `Task` に変わる |
| default export を named export にする、バレルファイルの公開範囲を絞る | パッケージ外の import が壊れる。公開ライブラリでは破壊的変更になる |
| オブジェクト・配列を不変にする | 呼び出し側が渡したオブジェクトの変更を前提にしていると動かなくなる |
| 型ガード・バリデーション（Pydantic など）を追加する | これまで通っていた入力で例外が発生するようになる |
| 裸の `except:` や広すぎる `catch` を絞る | これまで握りつぶしていた例外が呼び出し元に伝わる。この操作は定義上、振る舞いを変える |
| C# のクラスを `record` にする | `==` と `Equals` が参照の比較から値の比較に変わる。Dictionary のキーや HashSet での扱いも変わる |
| C# の switch 文を switch 式にする | どの分岐にも当たらないとき `SwitchExpressionException` が発生する |
| ループを LINQ にする、リストをジェネレータにする | 遅延評価になり、副作用の実行時点が変わる。複数回列挙すると処理が複数回走る |
| `os.path` を `pathlib.Path` にする | 戻り値が `str` から `Path` に変わり、文字列操作をしている呼び出し側が壊れる |
| 依存を `new` からコンストラクタインジェクションにする | コンストラクタのシグネチャが変わる。DI コンテナへの登録とライフタイムの指定が必要になる |
| デッドコード・未使用の抽象化を削除する | 動的 import、リフレクション、テンプレート（Angular のテンプレートから呼ぶメソッドなど）、外部パッケージから使われていると壊れる。SvelteKit のルートのファイル（`+page.ts` など）が export する `load`・`actions`・`GET` などは、どこからも import されていなくてもフレームワークが呼ぶ |
| Svelte 4 の書き方を Svelte 5 の runes に移行する（`$:` を `$derived` / `$effect` に、`export let` を `$props()` に、store を `$state` に） | 更新が実行される時点が変わる。`$derived` は値が読まれたときに計算され、`$effect` は DOM の更新の後に実行される。イベント修飾子や slot も書き方が変わる。リファクタリングではなく移行の作業として、コンポーネント 1 つずつ行う |
| `$effect` の中で代入している値を `$derived` に書き換える | 値が計算される時点が変わる。`$effect` の中で他の副作用（ログ、通信）も行っている場合は、その副作用の実行回数も変わる |

## 操作カタログ

### Bloat（肥大）

| 臭い | 見つけ方 | 操作 | 注意 |
|---|---|---|---|
| 長すぎる関数（Long Method） | コメントで区切られた処理のまとまりがある。1 画面に収まらない | 関数の抽出。まとまりごとに、何をするかが分かる名前の関数にする | 抽出した関数に渡す変数が 4 つ以上になるなら、先に変数の整理をする |
| 巨大なクラス（Large Class / God Class） | フィールドの一部だけを使うメソッドの集まりが複数ある | クラスの抽出。一緒に使われるフィールドとメソッドを別クラスに移す | 公開メソッドは元のクラスに残して委譲し、呼び出し側を変えない |
| 長すぎるパラメータリスト | 引数が 4 つ以上ある | Parameter Object の導入 | 呼び出し側もすべて直す |
| データの塊（Data Clumps） | 同じ 3 つ前後の変数が、複数の関数の引数やクラスのフィールドに一緒に現れる | 型またはクラスとして抽出する | |
| 基本データ型への執着（Primitive Obsession） | メールアドレス・金額・ID などを `string` や `number` のまま扱い、検証が各所に散らばる | Value Object または専用の型（TypeScript なら branded type）に置き換える | 生成時に検証を加えると振る舞いが変わる。検証の追加は別の操作として分ける |
| 深いネスト | if や for のネストが 3 段以上ある | ガード節・早期リターンで浅くする | 条件を反転するときは、ド・モルガンの法則で正しく反転できているか確かめる |
| マジックナンバー | 意味の説明が無い数値・文字列のリテラル | 名前付き定数に置き換える | 値は変えない |

### Object-Orientation Abusers（オブジェクト指向の誤用）

| 臭い | 見つけ方 | 操作 | 注意 |
|---|---|---|---|
| 型による switch（Switch on Type） | 種別を表す値で分岐する switch・if が複数箇所にある | ポリモーフィズムに置き換える。TypeScript では Discriminated Union も候補にする | switch が 1 箇所だけなら、置き換えの効果は小さい |
| 一時的フィールド（Temporary Field） | 特定のメソッドの実行中だけ値が入るフィールド | ローカル変数にする、または必要なときに計算するメソッドにする | 計算に副作用があると、実行される時点が変わる |

### Change Preventers（変更を妨げるもの）

| 臭い | 見つけ方 | 操作 | 注意 |
|---|---|---|---|
| 発散的変更（Divergent Change） | 1 つのクラスを、無関係な複数の理由で修正している（git log で確かめる） | 変更の理由ごとにクラスを分割する | 分割は複数の操作になる。1 操作ずつテストを通す |
| 散弾銃手術（Shotgun Surgery） | 1 つの変更のために多数のファイルを修正している | 関連するコードを 1 か所に移動する | |

### Dispensables（不要なもの）

| 臭い | 見つけ方 | 操作 | 注意 |
|---|---|---|---|
| 重複コード（Duplicate Code） | 同じ、またはほぼ同じ処理が 2 か所以上にある | 共通の関数に抽出する | 見た目が同じでも変更の理由が違うなら共通化しない。3 か所目が現れるまで待つ判断もある |
| デッドコード | 参照されていない関数・クラス・変数・import | 削除する | 「振る舞いが変わりうる操作」の削除の行を確認する |
| 投機的一般性（Speculative Generality） | 実装が 1 つしかないインターフェース、使われていない引数やフック | インライン化・削除で単純にする | 公開 API の一部なら削除しない |

### Couplers（過剰な結合）

| 臭い | 見つけ方 | 操作 | 注意 |
|---|---|---|---|
| 機能の横恋慕（Feature Envy） | 自分のフィールドより、他のクラスのデータを多く使うメソッド | データを持つクラスにメソッドを移動する | |
| 不適切な関係（Inappropriate Intimacy） | 他のクラスの private に近いフィールドを直接読み書きしている | インターフェースやメソッド経由のアクセスに置き換える | |
| メッセージチェーン（Message Chains） | `a.b().c().d()` のような呼び出しの連鎖。デメテルの法則の違反 | 委譲の隠蔽（Hide Delegate）。途中のオブジェクトにメソッドを追加する | |

### 関数の構成（Composing Methods）

| 操作 | 適用する場面 | 注意 |
|---|---|---|
| 関数の抽出（Extract Function） | まとまった処理に名前を付けたいとき | 元の箇所は抽出した関数の呼び出しに置き換える |
| 関数のインライン化（Inline Function） | 関数の本体が名前と同じくらい分かりやすいとき | 他から呼ばれている、または export されている関数は対象外 |
| 変数の抽出（Extract Variable） | 複雑な式の意味が読み取れないとき | 式に副作用があると評価回数が変わることがある |
| ループの分割（Split Loop） | 1 つのループで複数の値を集計しているとき | ループの回数が増える。性能が問題になる箇所なら利用者に確認する |

### 条件式の単純化（Simplifying Conditionals）

| 操作 | 適用する場面 | 注意 |
|---|---|---|
| ガード節の導入 | 例外的な条件の処理がネストを深くしているとき | |
| 条件の分解（Decompose Conditional） | 条件式が長く、何を判定しているか読み取れないとき | 条件式を関数に抽出し、判定内容を名前にする |
| 制御フラグの削除 | `found = true` のようなフラグでループや処理の継続を制御しているとき | `return`・`break`・`continue` に置き換える |

### 原則と臭いの対応

利用者が原則の名前で依頼したときは、次の対応で操作を選びます。

| 依頼の言葉 | 確認する臭い・操作 |
|---|---|
| 単一責任の原則（SRP） | 巨大なクラス、発散的変更 |
| DRY | 重複コード |
| KISS / YAGNI | 投機的一般性、デッドコード |
| デメテルの法則 | メッセージチェーン |
| 循環的複雑度・認知的複雑度を下げて | 深いネスト、長すぎる関数、条件の分解。可能なら計測ツール（ESLint の `complexity` ルール、`radon`、Visual Studio のコードメトリクス）で前後の値を示す |
| ボーイスカウト・ルール | 利用者が今回触ったファイルの中だけで、マジックナンバー・変数の抽出・名前の改善など小さな操作を 1〜2 個行う |

## 大きな変更の進め方

1 つの操作で済まない変更には、次の進め方を使います。いずれも計画を先に利用者に示し、了承を得てから始めます。

- **ゴールデンマスター**: テストが無く、特性テストを個別に書くのが難しいレガシーコードで使います。代表的な入力の集合を用意し、現在の出力をファイルに保存します。変更後に同じ入力で出力を取り、保存したファイルと差分を比べます。日時や乱数など毎回変わる値は、比較の前に固定するか除外します。
- **ミカド法**: 目標の変更を試し、壊れた箇所を前提条件として書き出し、変更を戻します。前提条件を 1 つずつ同じ方法で分解し、依存の木を作ります。木の葉（他に前提が無い変更）から順に適用します。木は Mermaid の `graph TD` で示します。
- **ストラングラーフィグパターン**: 旧実装の前に振り分けの層（ファサードやルーティング）を置き、機能単位で新実装に切り替えます。新旧で同じ入力の結果を比べられる状態を保ち、すべて切り替えてから旧実装を削除します。

## 言語別の操作

「振る舞いが変わりうる操作」の表に載っている操作は、適用前に利用者の了承を得ます。

### TypeScript / JavaScript

| 操作 | 内容 | 注意 |
|---|---|---|
| `any` の排除 | 適切な型を付ける。外部からの値は `unknown` で受け、型ガードで絞る | 型注釈だけなら実行時の動作は変わらない。型ガードで例外を投げる処理を足すと変わる |
| Optional Chaining / Nullish Coalescing | 冗長な null チェックを `?.` と `??` にする | `&&` と `\|\|` からの置き換えは、falsy な値で結果が変わる |
| 不変性 | 直接の変更をスプレッド構文に、型を `readonly` / `Readonly<>` にする | Svelte 5 の `$state` で作った配列やオブジェクトは、`push` や代入による直接の変更で画面が更新される。不変にする書き換えは、Svelte のコンポーネントの状態には適用しない |
| Discriminated Union | 種別による分岐を、判別用のプロパティと型の絞り込みで書く | `default` 節に `never` の網羅チェックを置く |
| async/await | Promise チェーンを async/await にする | `catch` の位置で、どの例外を捕まえるかが変わらないようにする |
| 関数の純粋化 | 外部状態の読み書きを引数と戻り値に移す | 呼び出し側の変更が必要になる |
| named export への変更 | default export を named export にし、バレルファイル（`index.ts`）の公開範囲を整理する | |

Angular のコードでは、コンポーネントのメソッドやプロパティがテンプレート（`.html`）から参照されていることがあります。名前の変更や削除の前に、テンプレートも検索します。

Svelte / SvelteKit のコードでは、次の点に注意します。

- **`.svelte` ファイルも検索の対象にします。** 関数や変数は、`<script>` の外のマークアップ（`{value}`、`onclick={handler}`、`bind:value`）からも参照されます。コンポーネントの props の名前を変えるときは、親コンポーネントでそのコンポーネントを使っている箇所（`<Child count={...} />`）もすべて直します。
- **SvelteKit のルートのファイル名と export 名は変えません。** `+page.svelte`・`+page.ts`・`+page.server.ts`・`+layout.ts`・`+server.ts`・`hooks.server.ts` などのファイル名と、そこから export する `load`・`actions`・`GET`・`POST`・`prerender` などの名前は、フレームワークが決まった名前で探します。
- **ロジックを `.svelte` ファイルの外に出すときは、runes を使うかどうかで拡張子を選びます。** `$state` などの runes を使うコードは `.svelte.ts` に、使わないコードは `.ts` に置きます。runes は `.svelte` と `.svelte.ts` / `.svelte.js` の中でしか使えません。
- **サーバーでだけ動くコードを、ブラウザでも動くファイルに移しません。** 秘密の値や DB を扱うコードは、`+page.server.ts`・`+server.ts`・`hooks.server.ts`・`$lib/server/` の中に置いたままにします。`+page.ts` の `load` はブラウザでも実行されます。

### Python

| 操作 | 内容 | 注意 |
|---|---|---|
| 型ヒントの追加 | 関数と変数に型ヒントを付ける。`from __future__ import annotations` を使う | 実行時の動作は変わらない。`mypy` で確かめる |
| リスト内包表記・ジェネレータ式 | 単純な for ループを書き換える | 内包表記の中に副作用のある処理がある場合は書き換えない |
| コンテキストマネージャ | `open` / `close` を `with` 文にする | |
| `@dataclass` / Pydantic | 辞書やタプルのデータをクラスにする | `d["key"]` でアクセスしている呼び出し側が壊れる。Pydantic のバリデーションは入力を拒否することがある |
| 例外処理の整理 | 裸の `except:` を具体的な例外にする | この操作は振る舞いを変える |
| デコレータ | 繰り返し現れる前処理・後処理をデコレータに抽出する | `functools.wraps` を付け、関数名と docstring を保つ |
| f-string / pathlib | `%` や `.format()` を f-string に、`os.path` を `pathlib.Path` にする | f-string は出力が同じになることを確かめる |

### C#

| 操作 | 内容 | 注意 |
|---|---|---|
| モダン構文 | パターンマッチング、switch 式、init-only プロパティを使う | switch 式の網羅性に注意する |
| Nullable Reference Types | `#nullable enable` を付け、null になりうる型に `?` を付ける | コンパイル時の警告が増えるだけで、実行時の動作は変わらない。`!` で警告を消すのは最小限にする |
| LINQ | 単純なループを `Select` / `Where` / `Aggregate` にする | 結果をすぐ使うなら `ToList()` で確定させる |
| record | 値として扱うクラスを `record` にする | 等価性の比較が変わる |
| 依存性の注入 | `new` で生成している依存をコンストラクタインジェクションにする | |
| async/await と Task | ブロッキング呼び出しを `await` にする | `.Result` や `.Wait()` を残すとデッドロックの原因になる。`AggregateException` で受けていた箇所は例外の型が変わる |
| パターンマッチング | `is` による型チェックとキャストの連続を、`is` パターンや switch 式にする | |

## 行わないこと

- 振る舞いを変える修正（バグ修正、機能追加、性能改善）をリファクタリングに混ぜない。気付いたバグは報告し、別の作業として扱う。
- テストが落ちている状態で次の操作に進まない。
- 落ちたテストを、テスト側を書き換えて通さない。特性テストの期待値を変えるのは、利用者が振る舞いの変更を了承したときだけにする。
