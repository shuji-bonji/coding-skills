# Code Review

コードレビューを、毎回同じ観点・同じ優先度の基準で行うための手順です。TypeScript（Angular・MCP サーバー）を主な対象にしていますが、観点の大半は言語に依存しません。

## 基本ルール

1. **コードは書き換えない。** このスキルの成果物は Code Review Report です。修正は利用者が指摘を選んでから、別の作業として行います。構造の改善（関数の分割、重複の共通化など）は safe-refactoring に引き継ぎます。
2. **すべての指摘にファイル名と行番号を付ける。** 場所を示せない指摘は書きません。
3. **確かめた指摘と、疑いの指摘を分ける。** コードを読んで、またはコマンドを実行して確かめたものだけを「確認済み」とします。呼び出し元を追い切れなかったものなどは「要確認」とし、何を確かめれば確定するかを書きます。
4. **linter・formatter・型チェックで見つかるものは、レビューの指摘にしない。** それらはツールの実行結果としてまとめて報告し、レビューはツールで判定できない点に使います。
5. **好みだけの指摘はしない。** 指摘には「放置すると何が起きるか」を書きます。書けない指摘は削除します。

## 手順

### 1. 対象と範囲を決める

- 差分のレビューか、ファイル・ディレクトリ全体のレビューかを確かめます。指定が無ければ、未コミットの変更（`git diff`）、なければ直前のコミット（`git show HEAD`）を対象にし、そのことを報告の冒頭に書きます。
- PR の番号や URL が渡された場合は、`gh pr diff <番号>` と `gh pr view <番号>` で差分と説明文を取得します。
- 差分のレビューでは、変更された行だけでなく、その行を呼び出している箇所と、変更された関数の呼び出し先も読みます。差分の外で壊れることがあるためです。

### 2. プロジェクトの前提を読む

- `CLAUDE.md`・`AGENTS.md`・`CONTRIBUTING.md` があれば読み、プロジェクト固有の取り決めを把握します。取り決めに反する点は、一般論より優先して指摘します。
- `package.json`（`scripts`・`engines`・依存のバージョン）、`tsconfig.json`（`strict` の設定）、ESLint の設定を確認します。
- ディレクトリ構成とエントリーポイントを確認し、依存の向き（どの層がどの層を参照してよいか）を把握します。

### 3. 機械で確かめられることを先に実行する

型チェック・lint・テストのコマンドを実行し、結果を記録します（例: `npx tsc --noEmit`、`npm run lint`、`npm test`）。実行できない環境の場合は、実行していないことを報告に書きます。

### 4. 観点ごとに確認する

下の「確認の観点」を 1 から順に確認します。各観点について、指摘があったか、問題なしか、対象外かを記録します。

### 5. 指摘を確かめる

報告の前に、指摘を 1 件ずつ見直します。

- 指摘したコードが本当にその動作をするか、該当箇所をもう一度読みます。
- 「null になりうる」「await が漏れている」などの指摘は、呼び出し元を追って、実際にその状態になる経路があるか確かめます。経路が見つからなければ「要確認」に下げるか削除します。
- 同じ原因の指摘が複数ある場合は、1 件にまとめて該当箇所を列挙します。

### 6. 報告する

下の「報告の形式」で Code Review Report を返します。

## 確認の観点

### 1. バグ・不具合

- 条件分岐で処理されていないケースはないか（`else` 側、switch の `default`、union 型の網羅）
- `null` / `undefined` になりうる値を、確かめずに使っていないか
- `await` の漏れ、`catch` されていない Promise はないか
- 空配列・空文字列・`0` のときに想定どおり動くか
- `TODO`・`FIXME`・仮の値（`'xxx'`、`12345` など）が残っていないか
- 境界値（`<` と `<=`、ループの開始と終了）を取り違えていないか

### 2. セキュリティ

- API キー・パスワード・トークンがソースや設定ファイルに書かれていないか
- 外部からの入力（HTTP リクエスト、ファイル、MCP のツール引数）を検証せずに、SQL・シェルコマンド・ファイルパス・HTML に渡していないか
- ファイルパスを組み立てるときに `..` による親ディレクトリへの移動を防いでいるか
- Angular で `bypassSecurityTrust*` や `innerHTML` に外部の値を渡していないか
- 権限の確認が必要な処理で、確認が抜けている経路はないか

### 3. エラー処理

- 例外を `catch` して何もせずに捨てていないか
- エラーメッセージが「何が起きたか」と「利用者が次に何をすればよいか」を含んでいるか
- 利用者向けのメッセージとログ出力が混ざっていないか。利用者向けメッセージの言語が統一されているか
- エラー処理の方法（例外を投げる・`Result` 型を返す・`null` を返す）がプロジェクト内で統一されているか

### 4. 型安全性

- `any` を使っている箇所をすべて挙げ、具体的な型・`unknown`・ジェネリクスで置き換えられるか
- `as` による型アサーションを、型ガード関数で置き換えられるか
- `[key: string]: unknown` のようなインデックスシグネチャで、型の検査が効かなくなっていないか
- 外部から受け取るデータ（API の応答、ファイル）を、Zod などで実行時に検証しているか

### 5. 検査の抑止

- `eslint-disable`・`@ts-ignore`・`@ts-expect-error` の箇所をすべて挙げます。
- それぞれについて、型定義の拡張（declaration merging）、型ガード、ラッパー関数で取り除けるか判断します。
- 取り除けない場合は、理由がコメントに書かれているか確認します。`@ts-ignore` は `@ts-expect-error` にできないか確認します（不要になったときにエラーで気付けるため）。

### 6. ハードコーディング

- `package.json` のバージョン番号と同じ値が、ソースにも書かれていないか
- 説明の無い数値・文字列のリテラル、同じ文字列リテラルの重複はないか
- 環境によって変わる値（URL、ポート番号、ファイルパス）がソースに書かれていないか

### 7. パフォーマンス

- ループの中で、ループの間に変わらない計算を繰り返していないか
- 配列の線形探索を繰り返している箇所を、`Map` / `Set` で置き換えられるか
- ループの中で外部データを 1 件ずつ取得していないか（N+1 問題）
- 互いに独立した非同期処理を、`Promise.all` を使わずに順番に実行していないか
- イベントリスナー・購読（`subscribe`）・タイマーの解除漏れ、上限の無いキャッシュはないか

### 8. 重複と不要なコード

- 同じロジックが 3 か所以上にコピーされていないか
- 使われていない関数・`import`・変数・引数はないか
- 同じ形の `try` / `catch` や分岐が繰り返されていないか

### 9. 構造と保守性

- 1 ファイルが 300 行、1 関数が 50 行を超えていないか（目安。超えたら分割を検討する）
- ネストが 3 段以上になっていないか
- モジュール間の循環参照、下位の層から上位の層への参照はないか
- 内部でしか使わない関数を不必要に `export` していないか
- 同じ概念に別々の名前を使っていないか。設定値が複数のファイルに散らばっていないか

### 10. テスト

テストを書くことを一般論として求めるのではなく、今回の変更に対してだけ確認します。

- 振る舞いを変えた箇所に、その振る舞いを確かめるテストがあるか
- バグ修正の場合、修正前に落ちて修正後に通るテストがあるか
- テストが実装の内部（private なメソッド、呼び出し回数だけ）に依存しすぎていないか

### 11. 技術スタック固有の観点

対象のプロジェクトに当てはまるものだけを確認します。

#### Angular

- 変更検知に `ChangeDetectionStrategy.OnPush` を使っているか
- `subscribe` に対応する購読解除があるか（`takeUntilDestroyed`、`async` パイプ、signal への変換）
- `subscribe` の中で別の `subscribe` をしていないか（`switchMap` などで置き換えられるか）
- 画面の表示を担うコンポーネントと、状態やサービスを扱うコンポーネントの責務が分かれているか
- NgRx で、副作用が Effect に、状態の導出が Selector に置かれているか。Reducer の中に副作用が無いか
- プロジェクトの Angular のバージョンで推奨される書き方か（standalone コンポーネント、`@if` / `@for`、`inject()`）。Angular CLI の MCP サーバーが使える場合は、`get_best_practices` の結果と照らし合わせます。
- RxJS の購読漏れや演算子の誤用は、rxjs-mcp が使える場合は `lint_rxjs` と `detect_memory_leak` の結果も添えます。

#### MCP サーバー

- stdio で動くサーバーで、`console.log` など標準出力への書き込みが無いか（標準出力は JSON-RPC の通信に使われるため、ログは標準エラー出力に書く）
- ツールの description が、LLM がツールを選ぶのに足りるだけ具体的か（何をするか、いつ使うか、何を返すか）
- 入力スキーマ（Zod）に `.strict()` が付いていて、`tools/list` の応答の `inputSchema` に `additionalProperties: false` が入っているか
- `readOnlyHint`・`idempotentHint`・`destructiveHint` などの annotations が実際の動作と合っているか
- ツールの失敗を、例外を投げるのではなく `isError: true` の結果として返しているか
- `structuredContent` を返す場合、`outputSchema` と一致しているか

#### Node.js / TypeScript 全般

- `tsconfig.json` で `strict: true` が有効か
- ESM と CommonJS が混在していないか
- `package.json` の `engines` に Node.js のバージョンが書かれているか

## 優先度の基準

優先度は観点の種類ではなく、放置したときの影響で決めます。

| 優先度 | 基準 | 例 |
|---|---|---|
| 🔴 高 | 実行時のバグ、データの不整合、セキュリティの問題 | 処理されない `null`、入力を検証しないパス結合、仮の値の残存 |
| 🔴 高 | 繰り返し実行されると性能が大きく落ちる | 呼び出しのたびの全件走査、N+1 問題 |
| 🟡 中 | 次に変更するときにバグを生みやすい | ロジックの重複、責務の分散、マジックナンバー |
| 🟡 中 | 型による検査が効かなくなっている | `any`、根拠の無い `as` |
| 🟡 中 | 変更した振る舞いにテストが無い | |
| 🟢 低 | 読みやすさ・一貫性の改善 | 命名の統一、同じ形の処理の繰り返し |
| 🟢 低 | 小さな構造の改善 | 型定義の置き場所、不要な `import` |

## 報告の形式

```markdown
## Code Review Report

- 対象: 未コミットの変更（git diff）/ src/tools/search.ts ほか 3 ファイル
- 読んだ範囲: 差分と、変更された関数の呼び出し元 2 か所
- ツールの実行結果: tsc エラー 0 件 / lint 警告 2 件（下の付録） / テスト 128 件成功・0 件失敗

### 総評
全体の評価を 1〜2 文で書く。

### 指摘

#### 🔴 1. （指摘の題名）
- 場所: src/tools/search.ts:42
- 観点: バグ・不具合
- 状態: 確認済み / 要確認（確定させるには何を確かめればよいか）
- 問題: 何が起きるか。どの入力・どの経路でそうなるか
- 修正案: 具体的なコード例
- 修正の種類: 振る舞いの修正 / 構造の改善（safe-refactoring で対応できる）

### 優先度のまとめ
| # | 優先度 | 場所 | 題名 | 状態 |
|---|---|---|---|---|

### 観点ごとの結果
| 観点 | 結果 |
|---|---|
| 1. バグ・不具合 | 指摘 2 件 |
| 2. セキュリティ | 問題なし |
| 11. Angular | 対象外 |

### 良い点
設計や実装で良かった点を具体的に書く。

### 付録: ツールの出力
lint の警告など、ツールが出した結果をそのまま載せる。
```

## 行わないこと

- コードを書き換えること。修正は利用者が指摘を選んでから行います。
- formatter が担う書式（インデント、引用符、改行の位置）の指摘。
- 対象の範囲を超えた、アーキテクチャ全体の作り直しの提案。必要だと判断した場合は、総評に 1 文だけ書きます。
- 「〜すべき」だけで、何が起きるかと修正案の無い指摘。
