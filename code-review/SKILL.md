# Code Review

変更をレビューし、確かめた指摘と承認できるかの判定を返すための手順です。TypeScript（Angular、Svelte / SvelteKit、MCP サーバー）を主な対象にしていますが、観点の大半は言語に依存しません。Google の Engineering Practices（レビューの基準と観点）、Conventional Comments（指摘の書式）、OWASP Code Review Guide（セキュリティの観点）、SmartBear と Cisco の調査（一度に読む量の上限）、Claude Code 公式の code-review プラグイン（誤検知の除外）をもとにしています。

## 基本ルール

1. **判定の基準は「変更によってコード全体の状態が良くなるか」とする。** 完璧であることは求めません。良くなるなら、細かい改善点が残っていても承認できると判定します。悪くするなら、小さな変更でも承認しません。小さな悪化の積み重ねを防ぐためです。
2. **コードは書き換えない。** 成果物は Code Review Report です。修正は利用者が指摘を選んでから、別の作業として行います。構造の改善（関数の分割、重複の共通化など）は safe-refactoring に、テストの追加は test-writing に引き継ぎます。
3. **確かめた指摘だけを出す。** すべての指摘にファイル名・行番号・根拠を付けます。根拠を示せない指摘は「要確認」に分けるか、削除します。指摘の数を増やすことより、誤った指摘を出さないことを優先します。
4. **今回の変更が持ち込んだ問題だけを指摘する。** 変更されていない行の既存の問題は指摘しません。気付いた場合は、報告の末尾に「対象外で気付いた点」として 1 行で書くにとどめます。
5. **ツールで見つかるものは指摘にしない。** linter・formatter・型チェック・テストの失敗は、ツールの実行結果として報告します。レビューはツールで判定できない点に使います。

## 手順

### 1. 対象を決める

- 指定が無ければ、未コミットの変更（`git diff` と `git diff --staged`）を対象にします。それも無ければ直前のコミット（`git show HEAD`）を対象にし、そのことを報告の冒頭に書きます。
- PR の番号や URL が渡された場合は、`gh pr view <番号>` で説明文を、`gh pr diff <番号>` で差分を取得します。PR がクローズ済み・ドラフト・自動生成（依存の一括更新など）の場合は、レビューを続けるか利用者に確かめます。
- 変更が 400 行を超える場合は、ファイルやモジュールのまとまりごとに分けて、手順 3〜5 をまとまりごとに行います。一度に読む量が 400 行を超えると、見落としが増えることが分かっているためです。合わせて、変更を分割できないかを総評で提案します。

### 2. 変更の意図を把握する

指摘を探す前に、変更が何をしようとしているかを理解します。レビューで最も時間がかかり、最も重要なのはこの段階です。

- PR の説明文・コミットメッセージ・関連する issue を読みます。
- `CLAUDE.md`・`AGENTS.md`・`CONTRIBUTING.md` があれば読みます。変更されたファイルと同じディレクトリや親ディレクトリにあるものも読みます。
- 変更の意図を 2〜3 文でまとめ、報告の冒頭に書きます。意図が読み取れない場合は、そのこと自体を `question` の指摘にします。

### 3. 機械で確かめられることを実行する

型チェック・lint・テストを実行し、結果を記録します（例: `npx tsc --noEmit`、`npm run lint`、`npm test`）。実行できない環境の場合は、実行していないことを報告に書きます。

### 4. 観点ごとに読む

次の順で読みます。

1. **全体を見る:** 変更されたファイルの一覧と差分の規模を見て、変更の中心になるファイルを特定します。設計に大きな問題があれば、細部を読む前に報告します。細部の指摘が無駄になるためです。
2. **中心になるファイルを読む:** 差分だけでなく、変更された関数を含むファイル全体と、変更された関数の呼び出し元・呼び出し先を読みます。
3. **残りのファイルを順に読む:** 人が書いたコードは全行を読みます。自動生成されたファイルやデータファイルは流し読みでかまいません。読まなかった範囲は報告に書きます。

読むときは、下の「確認の観点」を 1 から順に当てはめます。加えて、次の 3 つの読み方で確かめます。

- **取り決めとの照合:** `CLAUDE.md` などに明記された規則に反していないか。規則に明記されていない好みは指摘しません。
- **履歴の確認:** `git log -p -- <ファイル>` と `git blame` で、変更された行が過去にどういう理由で書かれたかを確かめます。過去のバグ修正を元に戻していないか、意図して置かれた処理を消していないかを見ます。
- **コード内のコメントとの照合:** 変更されたファイルにある「〜しないこと」「〜の順序を変えないこと」といったコメントに、変更が従っているか確かめます。

### 5. 指摘を確かめる

報告の前に、指摘を 1 件ずつ見直し、確信度を付けます。

| 確信度 | 基準 | 扱い |
|---|---|---|
| 高 | コードを読んで、またはコマンドを実行して、問題が起きる経路を確かめた | 指摘として出す |
| 中 | 問題が起きそうだが、呼び出し元を追い切れていないなど、確かめ切れていない | 「要確認」として出し、何を確かめれば確定するかを書く |
| 低 | 起きる経路が見つからない、または好みの問題 | 削除する |

次のものは、確信度にかかわらず削除します。

- 今回の変更より前から存在する問題
- バグに見えるが、読み直すとバグではないもの
- 経験のある開発者なら指摘しない細かすぎる点
- linter・型チェック・formatter・テストで検出されるもの
- `eslint-disable` などで、理由を書いたうえで意図して抑止されている箇所
- PR の目的として意図された振る舞いの変更

同じ原因の指摘が複数ある場合は、1 件にまとめて該当箇所を列挙します。

### 6. 報告する

下の「報告の形式」で Code Review Report を返します。

## 確認の観点

### 1. 設計

- 変更の中のコード同士の関係に無理がないか
- この変更は、このコードベースのこの場所に置くべきものか（共通ライブラリや別のモジュールに置くべきではないか）
- 既存の仕組みと整合しているか。既存の仕組みで済むものを新しく作っていないか
- 今は必要の無い汎用化や機能を入れていないか。将来の問題は、実際に必要になってから解きます

### 2. 機能

- 作者の意図どおりに動くか。その意図は、利用者とこのコードを使う開発者にとって望ましいか
- 処理されていないケースはないか（`else` 側、switch の `default`、union 型の網羅、空配列・空文字列・`0`・`null`・`undefined`）
- 境界値（`<` と `<=`、ループの開始と終了、ページングの最終ページ）を取り違えていないか
- 非同期処理で、`await` の漏れ、`catch` されていない Promise、応答の到着順が入れ替わったときの不整合（古い応答が新しい応答を上書きする）はないか
- 共有している状態を複数の処理から同時に書き換えていないか
- `TODO`・`FIXME`・仮の値（`'xxx'`、`12345` など）が残っていないか
- 画面に影響する変更は、動作を確かめた記録（スクリーンショット、手順）があるか

### 3. セキュリティ

- 外部からの入力（HTTP リクエスト、ファイル、URL パラメーター、MCP のツール引数）を検証せずに、SQL・シェルコマンド・ファイルパス・HTML・正規表現に渡していないか
- ファイルパスを組み立てるときに、`..` で親ディレクトリに移動されることを防いでいるか
- 認証と権限の確認が必要な処理で、確認を通らない経路はないか
- API キー・パスワード・トークンがソース・設定ファイル・ログ出力に含まれていないか
- エラーメッセージや応答に、スタックトレースや内部のパスなど外部に見せない情報が含まれていないか
- Angular で `bypassSecurityTrust*` や `[innerHTML]` に、Svelte で `{@html}` に、外部の値を渡していないか

### 4. 複雑さ

- 行・関数・クラスのそれぞれで、読んですぐに理解できるか。次に変更する人がバグを入れやすい書き方になっていないか
- ネストが 3 段以上になっていないか。1 関数が 50 行、1 ファイルが 300 行を超えていないか（目安）
- 同じロジックが 3 か所以上にコピーされていないか

### 5. エラー処理

- 例外を `catch` して何もせずに捨てていないか
- エラーメッセージが「何が起きたか」と「次に何をすればよいか」を含んでいるか
- エラー処理の方法（例外を投げる・`Result` 型を返す・`null` を返す）が、プロジェクトの既存のコードと揃っているか

### 6. 型安全性

- `any`、根拠の無い `as`、`@ts-ignore` を新しく持ち込んでいないか。持ち込む場合は理由がコメントに書かれているか
- 外部から受け取るデータ（API の応答、ファイル）を、Zod などで実行時に検証しているか

### 7. テスト

- 振る舞いを変えた箇所に、その振る舞いを確かめるテストが同じ変更の中にあるか
- そのテストは、コードが壊れたときに実際に失敗するか（期待値が実装をそのまま写しているだけになっていないか）
- バグ修正の場合、修正前に失敗して修正後に通るテストがあるか
- テストのコード自体が、不必要に複雑になっていないか

### 8. 命名

- 名前が、対象が何であるかを十分に表しているか。長すぎて読みにくくなっていないか
- 同じ概念に、既存のコードと別の名前を付けていないか

### 9. コメントとドキュメント

- コメントが「何をしているか」ではなく「なぜそうするのか」を書いているか。何をしているかの説明が必要なら、コードを単純にできないか
- 変更によって古くなったコメントや、不要になった `TODO` が残っていないか
- ビルド・テスト・利用方法・設定項目が変わる場合、README などのドキュメントも更新されているか

### 10. 一貫性と変更の分け方

- 規則が無い点は、周囲の既存コードに合わせているか
- 大規模な整形や名前の一括変更が、機能の変更と同じ差分に混ざっていないか。混ざっている場合は、変更を分けることを提案します

### 11. 技術スタック固有の観点

対象のプロジェクトに当てはまるものだけを確認します。現行の推奨は版によって変わるため、公式の情報源が使える場合はそちらを優先します（Angular CLI の MCP サーバーの `get_best_practices`、Svelte の MCP サーバーの `svelte-autofixer` と `get-documentation`、rxjs-mcp の `lint_rxjs` と `detect_memory_leak`）。

#### Angular

- `subscribe` に対応する購読解除があるか（`takeUntilDestroyed`、`async` パイプ、signal への変換）
- `subscribe` の中で別の `subscribe` をしていないか。検索のように新しい要求で古い要求を取り消すべき処理に、`mergeMap` ではなく `switchMap` を使っているか
- 変更検知に `ChangeDetectionStrategy.OnPush` を使っているか
- NgRx で、副作用が Effect に、状態の導出が Selector に置かれ、Reducer に副作用が無いか

#### Svelte

- 他の状態から計算できる値を、`$effect` の中で代入していないか。`$derived`（複雑な計算は `$derived.by`）で書けます。`$effect` は DOM の直接の操作や外部のライブラリとの連携など、限られた用途に使うものです
- `$effect` の中で、自分が読んでいる `$state` を書き換えていないか。無限に再実行されます
- 2 つの `$effect` が互いの値を更新し合っていないか。片方を `$derived` にし、もう片方は入力のイベントや関数バインディングで更新できます
- 1 つのプロジェクトの中で、Svelte 4 の書き方（`$:`、`export let`、`on:click`）と Svelte 5 の書き方（runes、`onclick`）が、方針なく混在していないか
- `$state` を使うロジックを `.svelte` ファイルの外に出す場合、ファイルの拡張子が `.svelte.ts` になっているか

#### SvelteKit

- 秘密の値（`$env/static/private`、`$env/dynamic/private`）や DB へのアクセスが、サーバーでだけ実行されるファイル（`+page.server.ts`、`+layout.server.ts`、`+server.ts`、`hooks.server.ts`、`$lib/server/`）に置かれているか。`+page.ts` の `load` はブラウザでも実行されます
- form actions と `+server.ts` で、入力の検証と権限の確認をサーバー側で行っているか。画面での非表示や `load` での確認だけでは、直接の要求を防げません
- サーバーで実行されるコードで、モジュールの最上位の変数に利用者ごとのデータを保存していないか。サーバーのプロセスは複数の利用者の要求で共有されるため、別の利用者にデータが見えます
- `load` の中で、互いに依存しない取得を順番に `await` していないか。`Promise.all` で同時に取得できます
- `load` の中の通信に、引数で渡される `fetch` を使っているか。グローバルの `fetch` を使うと、サーバー側での描画のときに cookie が引き継がれず、相対 URL も使えません

#### MCP サーバー

- stdio で動くサーバーで、標準出力への書き込み（`console.log` など）が無いか。標準出力は JSON-RPC の通信に使われるため、ログは標準エラー出力に書きます
- ツールの description が、LLM がツールを選ぶのに足りるだけ具体的か（何をするか、いつ使うか、何を返すか）
- `tools/list` の応答の `inputSchema` が、実際に受け付ける引数と一致しているか
- `readOnlyHint`・`destructiveHint`・`idempotentHint` などの annotations が実際の動作と合っているか
- ツールの失敗を、例外を投げるのではなく `isError: true` の結果として返しているか

## 指摘の書式

指摘は Conventional Comments の書式で書きます。そのまま PR のコメントに貼れるようにするためです。

```
<ラベル> (<blocking または non-blocking>): <要点を 1 文で>

<なぜ問題か。どの入力・どの経路で何が起きるか>
<修正案。必要ならコード例>
```

| ラベル | 使う場面 | 既定の扱い |
|---|---|---|
| `issue` | 実際に問題が起きる。修正案を必ず添える | blocking |
| `todo` | 小さいが、承認の前に必要な作業 | blocking |
| `question` | 意図が読み取れない、または確かめ切れていない（確信度「中」） | non-blocking |
| `suggestion` | 改善案。何をなぜ改善するかを書く | non-blocking |
| `nitpick` | 細かい点。数を絞り、1 回のレビューで数件までにする | non-blocking |
| `thought` | 今回の変更の範囲外だが、検討する価値がある考え | non-blocking |
| `praise` | 良い設計・良い実装。具体的に書く | non-blocking |

`praise` は、具体的に挙げられる点がある場合に必ず 1 件以上書きます。形だけの称賛は書きません。

## 判定

次の 3 つのいずれかで判定します。

| 判定 | 条件 |
|---|---|
| 承認できる | blocking の指摘が無い。non-blocking の指摘は残っていてもよい |
| 修正後に承認できる | blocking の指摘があるが、変更の方向は妥当 |
| 方針の見直しが必要 | 設計の観点で問題があり、細部を直しても解決しない |

## 報告の形式

```markdown
## Code Review Report

- 対象: PR #42「検索 API のページング対応」/ 変更 6 ファイル・+182 行・-40 行
- 変更の意図: 検索結果を 50 件ずつ返すようにし、続きを cursor で取得できるようにする。
- 読んだ範囲: 差分のすべてと、変更された関数の呼び出し元 3 か所。生成ファイル `src/gen/*.ts` は流し読み
- ツールの実行結果: tsc エラー 0 件 / lint 警告 0 件 / テスト 128 件成功・0 件失敗
- 判定: 修正後に承認できる

### 総評
判定の理由を 1〜3 文で書く。

### 指摘

#### 1. src/search/paginate.ts:42
issue (blocking): 最終ページで cursor が null のまま次の要求に使われる

`items.length === pageSize` のときだけ cursor を設定しているため、残りがちょうど 50 件のときに空のページを 1 回余分に返す。
（修正案のコード例）

#### 2. src/search/search.service.ts:18
praise: 古い応答を switchMap で取り消しているため、入力を連打しても表示が入れ替わらない

### 要確認
- src/search/cache.ts:30 — キャッシュのキーに利用者 ID が含まれていない。複数の利用者が同じプロセスを共有するかを確かめれば確定する

### 対象外で気付いた点
- src/legacy/util.ts の既存の `any`（今回の変更では触れていない）
```

## 行わないこと

- コードを書き換えること。修正は利用者が指摘を選んでから行います。
- formatter が担う書式（インデント、引用符、改行の位置）の指摘。
- 規則に書かれていない、好みだけの指摘を blocking にすること。
- 「〜すべき」だけで、何が起きるかと修正案の無い指摘。
- 変更の範囲を超えた、アーキテクチャ全体の作り直しの提案。必要と判断した場合は `thought` として 1 件だけ書きます。
